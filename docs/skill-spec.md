# 技能包规范

新增或修改技能包时按本规范执行。`tools/validate_skills.py` 会检查其中的硬性项。

---

## 1. 命名

- 目录名 = `<组>-<科目号>-<英文名>`，全小写、连字符分隔
- 组：`z`（资产）/ `f`（负债）/ `s`（损益）/ `a`（通用）
- 例：`z-1-2-bank-deposits`、`f-9-taxes-payable`、`s-14-credit-impairment`
- 辅助分析类用具名：`doc-ocr-extract`、`financial-statement-analysis`

## 2. SKILL.md

**frontmatter（必需）**：

```yaml
---
name: z-1-2-bank-deposits        # 必须与目录名一致
description: 一段话说明何时使用    # 含触发场景与触发词
version: 1.0.0
---
```

**正文必需章节**：

| 章节 | 内容 | 被谁消费 |
| --- | --- | --- |
| 技能来源与使用声明 | 归属、许可、免责 | 首次调用时逐字输出 |
| 六要素 | 审计目标 / 所需资料 / 所需数据 / 核对逻辑 / 底稿内容 / 输出格式 | agent 理解任务边界 |
| 程序分派表 | 标准 Markdown 表格，列：程序卡 / 程序名称 / 程序库来源 / 对应认定 / 执行方式 / 产出底稿 | 决定执行哪几张卡 |
| 一级复核清单 | 交付前逐项自查 | 质量门 |
| 边界与易错点 | 什么不做、常见错误 | 防越界 |
| 验证要点 | 如何判断结果可信 | 复核 |

**程序分派表必须是标准 Markdown 表格**。解析器靠它确定程序卡清单，表格格式错会导致程序卡识别为 0。

表头必须使用上表列出的名称（解析器**按表头名取列，不按列的位置**）。其中「执行方式」列可以省略（`s-1-revenue` 就没有），省略时该程序按"未声明"处理，运行时从程序卡 Steps 的 `【人工】` 标签补判；其余五列建议齐全。

## 3. dsl.json

以下是**实物格式**，与 `skills/*/dsl.json` 完全一致（以实际文件为准）：

```json
{
  "skill_id": "z-1-2-bank-deposits",
  "name": "货币资金·银行存款",
  "version": "1.0.0",
  "owner_role": "审计助理",
  "cycle": "Z",
  "group_code": "Z",
  "risk_level": "中",
  "description": "银行存款审计技能组（1002 科目，程序库 Z1002）……",
  "procedures": [
    {
      "id": "P01",
      "name": "银行存款余额明细表编制",
      "tools": ["recalc_check", "balance_confirm"],
      "human": false
    }
  ],
  "quality_gate": { "required_coverage_pct": 100 }
}
```

**字段说明**

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `skill_id` | 是 | 必须与目录名一致 |
| `name` / `description` / `version` | 是 | 与 SKILL.md frontmatter 保持同步 |
| `owner_role` / `cycle` / `group_code` / `risk_level` | 是 | 技能分类元信息 |
| `procedures[].id` | 是 | `P01`…`Pn`；规范型包用 `G0`/`G1`。正则 `^[A-Z]\d{1,3}$` |
| `procedures[].name` | 是 | 程序名，含「（强制）」标记的会被识别为强制程序 |
| `procedures[].tools` | 否 | 确定性工具标识数组。**可缺省**，缺省表示该程序无工具依赖（纯判断类） |
| `procedures[].human` | 否 | 布尔。**可缺省；缺省 ≠ `false`**，表示"未声明"，运行时按保守策略处理 |
| `quality_gate.required_coverage_pct` | 是 | 程序覆盖率要求，银行存款为 100 |

**dsl.json 不承载的字段**（不要往这里写，写了也会被忽略）：

| 想表达的内容 | 正确位置 |
| --- | --- |
| 对应认定（E/C/A/V/P） | `SKILL.md` 程序分派表「对应认定」列 |
| 产出底稿索引号（如 `Z-1-2-04`） | `SKILL.md` 程序分派表「产出底稿」列 |
| 程序库来源（如 `Z1002 程序2`） | `SKILL.md` 程序分派表「程序库来源」列 |
| 执行方式（自动 / 人工为主） | `SKILL.md` 程序分派表「执行方式」列 + 程序卡 Steps 的 `【人工】` 标签 |
| 程序间依赖顺序 | 技能包的 `SKILL.md` Steps 第 3 条（文字描述），由运行时配置落成 DAG |
| 程序详情（输入 / 步骤 / 质量门 / 升级路径） | `procedures/Pxx-*.md` 程序卡 |

**为什么要这样切分**：程序分派表是给人读的完整台账，dsl.json 只放机器必须精确匹配的那几项（id / 名称 / 工具 / 是否人工）。重复存放必然漂移——银行存款包就出现过 `dsl.json` 写 `human: false`、而分派表写「自动+人工判断」的情况。

**`human` 缺省时的判定规则**（运行时实现，写在这里供技能作者遵守）：

```
需要人工 = dsl.human 为 true
        或 分派表「执行方式」含"人工"
        或 程序卡 Steps 含【人工】
```

任一命中即需人工。**不允许**用 `human: false` 把分派表里的人工要求降下来。

## 4. 程序卡文档

路径：`procedures/P01-<名称>.md`

必需小节：

- **输入**：需要哪些资料、哪些字段
- **步骤**：可执行的动作序列
- **质量门**：什么条件下算通过（不通过要升级）
- **升级路径**：缺数据 / 有差异 / 超出判断范围时怎么办

## 5. 底稿制式

所有产出底稿必须遵循 `skills/auditox-wp-standard/SKILL.md`：

1. 一、项目基本信息
2. 二、审计目标和程序说明
3. 三、审计程序执行结果
4. 四、审计说明

**副本先行**（先复制模板再填）+ **修订记录**（每次改动留痕）。

资料不足以支撑四段式时，用三段式兜底：审定表 / 明细表 / 凭证抽查表。

## 6. 更新记录

`CHANGELOG.md`，倒序表格：

```markdown
# 更新记录 · 银行存款

| 更新日期 | 更新内容 |
| --- | --- |
| 2026-10-01 | 新增 P10 披露检查；修正 P04 调节表勾稽口径 |
| 2026-09-23 | 首次发布 |
```

只记技能内容变更，不记分发渠道动作（上架、打包、上传等）。

## 7. 版本号

| 变更 | 版本 |
| --- | --- |
| 修错别字、调表述 | patch |
| 新增程序卡 / 模板 / 工具映射 | minor |
| 改结构、断后向兼容 | major |

## 8. 提交前自检

```bash
python tools/build_index.py
python tools/validate_skills.py
```

两项通过再提交；CI 会跑同样的检查。
