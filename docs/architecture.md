# 架构说明

## 分层

```
┌─────────────────────────────────────────────┐
│  Agent 运行时（规划中：agent/）              │
│  路由 · 编排 · 工具注册 · 模型选择            │
└──────────────────┬──────────────────────────┘
                   │ 读 registry/skills.json 发现技能
┌──────────────────▼──────────────────────────┐
│  技能层（skills/，纯内容，无运行时依赖）      │
│  技能组 / 总控型 / 工具型 / 规范型            │
└──────────────────┬──────────────────────────┘
                   │ 调确定性工具，按制式产出
┌──────────────────▼──────────────────────────┐
│  产出层：四段式底稿 · 异常清单 · 运行日志     │
└─────────────────────────────────────────────┘
```

**核心约束**：技能层必须能被任意 agent 直接读取使用，不绑定特定运行时。运行时是可替换的，技能是资产。

## 四种技能形态

| 形态 | 判别 | 职责 | 例 |
| --- | --- | --- | --- |
| `skill-group` | 有 `procedures/` + `dsl.json` | 一个科目一套实质性程序，程序卡驱动 | `z-1-2-bank-deposits` |
| `orchestrator` | 有 `roles/` 子目录 | 识别任务类型与深度，路由到子技能 | `heavy-asset-financial-analysis` |
| `tool` | 有 `scripts/`，无 `roles/` | 单体执行，按工作方法跑 | `financial-statement-analysis` |
| `standard` | 只有 `SKILL.md` + `dsl.json` + `templates/` | 全局制式规范，被其他技能引用 | `auditox-wp-standard` |

判别靠**结构信号**，不靠包名约定。新增包只要结构正确，`tools/build_index.py` 自动归类。

## 数据流（单次任务）

```
用户给资料
   │
   ├─ 扫描件/照片/PDF ──→ doc-ocr-extract ──→ 结构化 JSON（带页码坐标溯源）
   │
   ▼
科目技能组 SKILL.md ──→ 程序分派表 ──→ 选定程序卡
   │
   ▼
程序卡 Pxx.md ──→ 输入 / 步骤 / 质量门 / 升级路径
   │
   ├─ 能确定性计算的 ──→ 调工具（勾稽、重算、抽样、索引号）
   │
   ▼
auditox-wp-standard 制式 ──→ 四段式底稿 + 异常清单
   │
   ▼
一级复核清单自查 ──→ 交结果（差异项标注「待人工确认」）
```

## 程序卡与工具的关系

`dsl.json` 的 `procedures[]` 是程序卡的机读声明：

```json
{
  "id": "P04",
  "tools": ["recon_statement_recalc", "threshold_flag"],
  "human": false
}
```

- `tools` 列出该卡应调的确定性工具；为空则纯判断类程序
- `human: true` 表示必须人工执行，agent 只准备资料
- 工具实现不在本仓库（属运行时侧），仓库只声明契约

## 为什么不用「一个大 skill」

- **可组合**：科目之间可交叉引用（如应收 + 收入截止测试）
- **可替换**：单个科目重写不影响其他
- **可复核**：程序卡粒度与审计底稿索引号一一对应，编制-复核分离
- **可验证**：每包带 `tests/` 黄金用例，改技能后能回归

## 升级为 agent 项目的路径

1. 建 `agent/` 目录，放运行时配置（模型、工具注册、路由策略）
2. `agent/router.md` 定义科目路由与编排规则
3. 保持 `skills/` 纯内容层，运行时通过 `registry/skills.json` 发现
4. **不得**把业务逻辑写进 `skills/`——技能必须脱离运行时也能用
